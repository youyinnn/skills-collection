# 研究工作流

## 1. 定方向的顺序

顺序不能颠倒:

1. 确认目标场地与处境约束(截稿日、页数、能不能换场地;涉及人类参与者时,伦理审批要多久)。
2. 列用户的第一作者成果。只有第一作者的才能当支点;合作者是第一作者的不算。
3. 这些成果欠了什么:用户自己的论文里写下、但还没兑现的。
4. 有没有人做过:先查,再设计。
5. 才谈怎么做。

外部论文只有两种用途:场地层面的信号(这个场地收什么样的论文),或者划清界限的对照物。不当结构模板。每次要引一篇外部论文来塑造建议前,先问:这是助手自己的偏好,还是用户的需要?

定下来的事写进 CLAUDE.md 的「已确立的事实」,之后不再重新论证:目标场地、可当支点的成果与不可当支点的成果、已排除的方向与理由、实验资产。

## 2. 八种判断错误

| 错误 | 是什么 | 怎么防 |
|---|---|---|
| **范本倒推** | 先在外面找一个够热、够漂亮的范本,再回头在用户的成果里找能对上的 | 按第 1 节的顺序走 |
| **填空式断言** | 在建议的转折处用听起来合理、但没核实的话填空(「这个会议欢迎负面结果」「这两篇综述指出了这个缺口」) | 影响决策的判断句要么给可核验的出处,要么标「推测/无证据」;「没人做过」要标明检索性质(关键词零散检索不等于系统检索) |
| **问题本身没查出处** | 给每条结论都标了出处,唯独没标「这个查证本身是谁提的」,于是在评估助手自己立的问题 | 开始查证、评估、筛选前先写「本次判断标准出自:___」,写不出就标「我自立」;自己引入的新术语视同自立判据,要标出处、解释词义 |
| **比喻与模糊修辞** | 用比喻或借来的术语代替字面陈述;一句话去掉比喻就不成立,说明它本来没有内容 | 判据写成可逐项核对的字面陈述,并给一个判定实例;跟用户说话举真实案例;论文里不用借来的术语与自造名目(工具名与文中先定义后使用的术语不算,见 `references/project-types/tool-paper.md`) |
| **自框自评** | 先把别人(尤其导师)的话改成好辩护的形状,再评估自己改的版本 | 引用他人的方向逐字保留原动词;改写要标明并说明为什么;评估前确认评的是谁的版本 |
| **凭空加障碍** | 把一个本来不成立的约束当硬约束反复强调,让可行的路显得走不通 | 用别人的话设约束前,先确认那句话的完整语义,包括反面(「拿不出更好的计划就按我的方向」反过来读就是「拿得出就不必按」) |
| **「0 篇」当利好** | 自己语料里 0 篇,就以为没人做过 | 用于决策前补一轮语料外检索,标明检索性质;同时写明 0 篇的另一面:也没有读者熟悉的同型先例可依附 |
| **材料换用途不重核** | 一份为论证 A 收集的材料,拿去论证与 A 相反的 B | 材料用途变了,重新核它是否支持新用途、当初是怎么收集的 |

## 3. 文献

- 检索先写预登记协议:查询式在跑之前写定,纳入与排除标准前置,标明检索性质。
- 一切检索走浏览器(用户自己登录机构账号),不用命令行或脚本调文献 API;核 DOI、核场地也算。命令行接口会反复被限流。
- PDF 统一用一种转换工具转成 markdown;转出的文本只作检索与读节,逐字引文回 PDF 核;拿不到 PDF 的从出版方或 PMC 的 HTML 抽,文件头写来源。
- 新文献入 bib 前在源头核(Crossref、arXiv、DBLP、出版方页面),查不到的字段留空不猜。
- 推荐加或删一处引用前,先查它在本项目里的来历;说「审稿人没提」前先打开报告核。
- 引用核查只报告;每处引用都要找到原文的逐字依据。

## 4. 实验与算力

- 模型训练与大规模评估不在用户的本机跑,连计时用的试跑也不跑;报成云 GPU 作业,由用户排。看可行性读 README 与脚本即可。单测、小例子可以在本机跑,跑之前说一句。
- 云 GPU 主机:按约定频率监控,跑完拉回结果、核数量,数对就关机,不另问。
- 付费 API 调用:跑之前报调用数、预计花销与耗时,等用户允许;跑完报 token、花销与耗时;问成本时钱和时间一起答。重跑、试探、格式检查都算。
- 锁定 API 托管方之前,看它的统计页(延迟、吞吐、可用率、量化),不只看价格。
- 每份运行日志在运行台账里有一行(用途、状态、模型、档位、调用数、花销、时长),新日志出现的同一轮补上。
- 说数据丢了之前,查所有副本与压缩包;问能不能恢复时,先答能或不能、多少。
- 往代码仓移植修复前,先看上游还有哪些提交没并进来;用 merge,不用 rebase。
- 统计判定照目标场地的惯例,先查同场地论文怎么报,不自立门槛。
- 按文件可得性或运行状态形成的子集,按这个原因命名,不冠以领域名。
- 设计里每一步的理由先自己检验;两步做同一件事就去掉一步;为留住一步而补的理由最可疑。

## 5. 标注

下面四条适用于给条目贴标签的标注。定性研究的主题分析见 `references/project-types/human-participants.md` 第 7 节;研究的就是 LLM 判断得对不对时,见 `references/project-types/derived-project.md` 第 5 节。

- 编码规则从任务提示与研究问题抽象定义;不列争议条目里出现的词,也不在规则来源的条目上验证规则。
- 给人与给 LLM 的标注材料从同一份文本生成,发出前并排核一遍。
- LLM 标注人当人类标注人对待:分歧照报,按事先定的程序裁决;不按一致率调编码本,也不按一致率挑标注人。
- 编码本与一致性统计量在看结果之前定下、冻结。

## 6. 复现包

1. 写一个构建脚本,按论文 Data Availability 的清单从各仓库拷文件进一个不进库的目录。
2. 只在副本上去作者信息(注释里的原话与署名、本机路径、用户名、云项目名、真人标注员名),全文扫描零命中才算建成。
3. 核验:在临时副本里按 README 重跑分析,产物逐字节比对。
4. 大文件(模型权重、逐样本结果)放外链存储,README 写下载表与校验和;托管用支持匿名只读链接的平台,链接显示匿名后才算好。
5. README 写明训练时的软件版本与锁定的依赖;第三方许可回源核对。

有人类参与者时,复现包放什么、扫描查什么见 `references/project-types/human-participants.md` 第 9 节;工具论文的 artifact evaluation 包与重跑结果怎么比见 `references/project-types/tool-paper.md` 第 4 节。
