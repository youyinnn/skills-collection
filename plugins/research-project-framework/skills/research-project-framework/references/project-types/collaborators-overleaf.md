# 补充:合作者直接改论文,或论文在 Overleaf 上编译

这两种情况常常一起出现,所以写在一份里。这份里的规则在冲突处优先于核心文档。

**例子:** 核心框架规定「没有任何会话日志记录的改动,是用户自己在编辑器里改的,随文件一起提交」。合作者从 Overleaf 推来的改动也没有会话日志,照这条做,就会以用户的名义提交,还报成「用户自己改的」。

## 1. 论文仓

- 论文仓从 Overleaf(git 桥或 GitHub 同步)或合作者已经建好的仓克隆,不要在本地 `git init` 再接远端:两边历史无关,推不上去。分支用远端实际在用的那个。
- 目录结构先和合作者商定,定了再填 `scripts/config.py` 的 `PAPER_SECTION_DIR`。
- 每次改 .tex 之前先拉取;改完由用户推送,或在用户定好的时点推送;有冲突列给用户,不整块取本地的版本。
- 论文仓不提交 PDF(优先于 `references/project-management.md` 第 4 节第 3 步):合作者一改,提交的 PDF 就过时,两边都提交还会出二进制冲突。要留底就放项目库,写明对应的论文仓提交号。

## 2. 本机不编译时

- 编译由 Overleaf 做。每次编译后,把编译日志(.log)和 PDF 下载到项目库的固定位置(例如 `derived/overleaf/`)。助手只依据这里的文件报错误、未定义引用、页数,做匿名检查和模拟评审的快照;没有这两样文件,就不说「编译通过」。
- 压尾巴要一处处试编:助手列出候选,用户在 Overleaf 上逐个试,回报这段变成几行。
- 编译锁和本地格式化工具都用不上。

## 3. 合作者的文字(优先于 `references/writing-workflow.md` 第 2 到 4 节)

- 作者们写的句子都不动。要动合作者的句子,先列给用户定,并告知那位合作者。优化、压尾巴都照这条。
- 只格式化本会话改过的行,或者干脆不跑格式化工具;格式约定和合作者商定。整份文件重新排版,合作者同时在改时会整片冲突。
- 重跑出图脚本之前先拉取;合作者对图文件的手改,和用户的手改一样,先同步进脚本再重跑。

## 4. 合作者的改动与决定(优先于 `references/project-management.md` 第 1、4 节)

- 没有会话日志记录的改动,先用 `git log`、`git status` 查是谁的:合作者的提交、合并到一半,还是用户的手改。查不清就问用户,不替任何人认领。
- 决定表的「谁」包括合作者。CLAUDE.md「已确立的事实」加一栏「作者与分工」:谁负责哪几节、哪类事由谁定。
- 合作者的意见(Overleaf 评论、.tex 里的 % 注释、邮件)和导师意见一样逐字存,不进扫描与改写;% 注释和评论不擅自删。
- 仪表盘的「等你一句话」只算 `decision_by` 填的是用户的卡;填合作者或导师的,另列「等别人」(要改 `Home.md` 里 `waiting` 那一组的筛选条件)。
