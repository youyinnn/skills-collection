# 补充:工具或方法论文

提出一个工具或方法、并和基线比较的论文按这份来。这份里的规则在冲突处优先于核心五份。

**例子:** 核心框架规定复现包要在临时副本里重跑,产物逐字节相同才算核验通过。工具论文的复现包要重跑工具本身,耗时、超时每次都不一样;照这条,复现包永远核验不过。

## 1. 基线与被测对象

- 写下选了哪些基线、排除了哪些、为什么。
- 用原作者发布的版本和推荐配置,记下版本号。
- 同一批被测程序、同一台机器、同样的时间与内存上限;崩溃和超时怎么计,事先写定。
- 调参的投入和基线对等;开发时用的程序和评估用的程序分开,不在评估集上调工具。

## 2. 性能测量

- 写下在哪台机器上量(型号、核数、内存)、每项重复几次、报什么统计量、超时设多少,和基线同机同条件。
- 运行台账的字段换成:工具提交号、基线版本、被测程序集版本、配置、机器、耗时、结果文件。`scripts/agent_runs_ledger.py` 只认 LLM 调用的日志,工具实验要照它另写一个,或改它的字段。

## 3. 写作

- 工具名和文中先定义后使用的术语可以用,不算「自造名目」(优先于 `references/research-workflow.md` 第 2 节与 `references/writing-workflow.md` 第 5 节);仍要查一词一义。
- 方法节和实现节的出处可以是代码仓的某个提交和设计文档,写明提交号;稿子和实现对不上,artifact evaluation 时会被查出来。
- 量范文的九节里没有方法(Approach)节和实现(Implementation)节的量法,起稿前先补。

## 4. 复现包与 artifact evaluation

- 投稿用的匿名包和录用后的 artifact evaluation 包分开建。
- artifact evaluation 包通常要:非匿名;带 DOI 的永久存档(例如 Zenodo);Docker 或虚拟机镜像;工具自己的 LICENSE;README 写硬件需求和预计耗时;半小时内能跑完的冒烟测试;论文里每张表、每张图对应的命令,和缩小规模的配置;与论文数字对应的工具版本标签。具体要求以当年的征稿为准。
- 匿名包去作者信息的扫描还要查:包名或命名空间、构建文件里的作者字段、源码的版权头与 LICENSE、镜像所在的账号、git 远端地址。
- 重跑工具得到的结果(耗时、超时、随机性带来的差异)按事先定好的容差比,不要求逐字节相同;从存档结果重算的分析产物才逐字节比。
